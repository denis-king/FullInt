# FullInt64 vs BigInteger after the optimizations — 2026-11-14

State at `2d4865a`: Mult asm fix, one allocation per result, one-word C# paths, Add/Sub asm
rewrite, short calls without the GC transition, Karatsuba from 64 limbs, Toom-3 from 256 limbs,
ArrayPool for large work buffers. Same suite and setup as

now with N = 4096 too. Raw data: [2026-11-14-api-after-optimizations.csv](2026-11-14-api-after-optimizations.csv).

Absolute, largest size:

| Op, N = 4096 | FullInt64 | BigInteger |
|---|---|---|
| Add | 2.98 µs | 9.92 µs |
| Mult | 1.51 ms | 7.97 ms |
| Div 8192 / 4096 | 21.1 ms | 323 ms |

Allocated bytes match BigInteger for Add and Mult at every size. Div allocates its quotient only;
at N = 1024 it is still 2× BigInteger because the 1025-word quotient starts with a zero word and
is copied once to its trimmed size (at 4096 the top word is not zero and nothing is copied).

Div at N = 1 (2 words / 1 word) is the remaining case slower than BigInteger. Div at 16–64 is the
schoolbook asm against BigInteger's; the ratios there moved between runs mostly on the BigInteger side.
