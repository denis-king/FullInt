# ARMv7 (32-bit Linux): FullInt against GMP and BigInteger

2026-11-27. Oracle Ampere A1 (Neoverse-N1) running AArch32 code natively: an `ubuntu:24.04` armhf container (`--platform linux/arm/v7`), pinned to one core (`--cpuset-cpus=1`). C++: GCC 13, `-O3`, against GMP 6.3 (Ubuntu's armhf package, `fullint_bench_api`). .NET: .NET 10.0.15 (linux-arm), `FullInt.Benchmarks cross`, both libraries warmed up per operation and size. A word is 64 bits; the operands are random, `div` / `mod` a 2N-word dividend by an N-word divisor.

Every kernel of the ARMv7 core is in assembly (`FullInt.Asm/Sources/arm32`, see [PLATFORMS.md](../PLATFORMS.md)) except the squaring and the approximate quotient. Raw times: [the C++ CSV](2026-11-27-arm32-cpp-vs-gmp.csv), [the .NET CSV](2026-11-27-arm32-net10.csv).

After this run the shifts' loops were split by s < 32 / s >= 32 (four register shifts a word instead of eight): `shl` / `shr` 0.88-1.46 (was 1.0-2.2).

Below 1: the operations on 1-8 words that allocate their result. On 32-bit ARM the runtime allocates a `ulong[]` through its 8-byte-alignment path: `new ulong[2]` takes 101 ns there, `new uint[4]` (BigInteger's 16 bytes) 37 ns - that, not the kernels, sets the time of a short result. `cmp` from 32 words in this run went through a C# loop (no vectors in .NET on ARMv7); it now goes to the kernel from 32 words: 1.7-2.8.
