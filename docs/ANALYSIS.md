# FullInt — анализ проекта и план выхода в NuGet

*Состояние на 2026-11-11, ветка `master` (`6a6efcf`) + незакоммиченные правки в `BuildWin.bat`, `FullInt.AsmForNet.csproj`, `FullIntBigTest.cs`.*

## 1. Коротко

| | |
|---|---|
| **Что это** | Библиотека целых чисел произвольной длины для .NET: лимбы по 64 бита, горячие операции на x86-64 ассемблере (NASM) через P/Invoke, управляемый C#-fallback. |
| **Объём** | ~8 тыс. строк: ~2,1 тыс. C# в ядре, ~1,1 тыс. asm, ~1,8 тыс. тестов, плюс legacy-проекты. |
| **Что работает** | На Windows x64 в двоичном (hex) режиме: `+ − × ÷ %`, сравнение, `pow`, разбор и вывод десятичных строк. 20/20 hex big-тестов (до 2048 бит) проходят против `System.Numerics.BigInteger`. |
| **Что не работает** | Полный прогон тестов **падает** (`AccessViolationException`); деление иногда ошибается; десятичный режим (`IsDec`) на asm-пути считает неверно; на всех платформах, кроме Windows x64, библиотека фактически неработоспособна (fallback не дописан). |
| **Готовность к NuGet** | Нет. Нужны: исправление 4 критичных багов, рабочий fallback, публичный API без утечки внутренностей, сборка нативных библиотек в CI, упаковка `runtimes/{rid}/native`. |

## 2. Оценка идеи

**Сильные стороны**

- **64-битные лимбы — реальное преимущество.** `System.Numerics.BigInteger` до сих пор хранит число в `uint[]` (32 бита). Школьное умножение на 64-битных лимбах выполняет в 4 раза меньше умножений-слов, а `mul`/`adc` на x64 и `mul`/`umulh`/`adcs` на ARM64 дают 128-битный результат за одну-две инструкции. Это та же причина, по которой GMP быстрее любой «чистой» реализации.
- **Слоистая архитектура** (`FullInt64` → `FullInt64Engine` → `IFullIntCore` → нативное ядро / C#-fallback) уже заложена — это правильная основа для мультиплатформенности.
- **Дифференциальное тестирование против `BigInteger`** на случайных данных — правильная стратегия для арифметики; её стоит усилить, а не заменять.

**Слабые стороны и реальность рынка**

- Ниша занята: `BigInteger` (встроен, бесплатен, стабилен, с Karatsuba на больших числах), обёртки над GMP/MPIR для .NET, BouncyCastle `BigInteger` для криптографии. Чтобы библиотеку выбирали, она должна **заметно** обгонять `BigInteger` на каком-то классе задач и давать то, чего у него нет.
- **Чем отличаться** (в порядке реалистичности):
  1. Скорость на больших числах (от 1–10 тыс. бит) за счёт 64-битных лимбов + Karatsuba/Toom + быстрая конвертация в строку. Ради этого стоит делать проект.
  2. API без аллокаций: `Span<ulong>`-операции и операции «в существующий буфер» (`BigInteger` всегда аллоцирует).
  3. Generic math (`INumber<T>`, `IBinaryInteger<T>`), чтобы `FullInt` подставлялся в обобщённый код.
  4. Длинные дробные числа (`BigDecimal`/`BigFloat`) поверх того же ядра — у .NET своих нет.
- **Вывод:** идея жизнеспособна как быстрая библиотека для больших чисел с zero-alloc API и расширением на вещественные. Как «ещё один BigInteger» — нет.

## 4. Архитектурные рекомендации

### 4.1. Модель «mpn-примитивы на asm, алгоритмы на C#»

Сейчас asm реализует целые алгоритмы (полное деление, перевод в строку). Это дорого переносить на каждую платформу и сложно отлаживать. Лучше сделать как в GMP:

- **Нативный слой — 8–10 маленьких ядер** на каждую платформу: `add_n`, `sub_n`, `add_1`, `sub_1`, `mul_1`, `addmul_1`, `submul_1`, `mul_basecase`, `sqr_basecase`, `divrem_1`, `lshift`, `rshift`, `cmp`. Каждое — 20–80 строк, легко портируется на ARM64 и легко тестируется.
- **C#-слой** — всё остальное: Karatsuba/Toom/NTT, алгоритм D Кнута (внешний цикл, а `submul_1` — в asm), Burnikel–Ziegler, конвертация строк «разделяй и властвуй», `pow`, `gcd`, `modpow`.
- **Managed fallback** реализует те же примитивы на `Math.BigMul` / `UInt128` и поэтому всегда корректен. Нативное ядро — только ускоритель. В тестах оба ядра прогоняются на одних и тех же данных.

### 4.2. Убрать `IsDec` из арифметического ядра

Хранение в базе 10¹⁹ удваивает сложность каждого алгоритма, и в asm оно уже сломано (A4). Ядро должно быть только двоичным (2⁶⁴); десятичная система — это только формат строки. Если нужна «быстрая десятичная печать», правильный путь — быстрая конвертация (D&C, §ALGORITHMS), а не другая база хранения.

### 4.3. Little-endian порядок лимбов

Сейчас `value[0]` — старший лимб. Если перейти на младший-первый (как GMP, `BigInteger`, Java):
- нормализация длины — это просто `length--`, без сдвига массива и без `DeleteZeros().ToArray()`;
- Karatsuba берёт половины через `span.Slice(0, n)` / `span.Slice(n)`;
- рост числа (перенос) — запись в конец, без перекладывания;
- проще интероп с `BigInteger.TryWriteBytes(isBigEndian:false)` и GMP.

Менять это нужно **до** публикации 1.0 — потом это ломающее изменение.

### 4.4. Публичный тип

```csharp
public readonly struct FullInteger :           // имя на выбор
    IBinaryInteger<FullInteger>, ISignedNumber<FullInteger>,
    IComparable<FullInteger>, IEquatable<FullInteger>,
    ISpanFormattable, ISpanParsable<FullInteger>, IUtf8SpanFormattable
{
    private readonly ulong[]? _bits;   // little-endian, нормализован, null → помещается в _small
    private readonly int _sign;        // -1/0/+1, ноль всегда +0
    ...
}
```

- Неизменяемый, без публичного доступа к массиву; доступ — через `TryWriteBytes`, `GetBitLength`, `CopyTo(Span<ulong>)`.
- Малые значения (|x| < 2⁶³) — без массива (как `BigInteger._sign`).
- Отдельно — низкоуровневый статический API `FullIntOps.Add(ReadOnlySpan<ulong>, ReadOnlySpan<ulong>, Span<ulong>)` для zero-alloc сценариев.
- `Pow` — метод, а не `^`; `Parse`/`TryParse` с `NumberStyles`, а не неявный `string`.
- TFM: `net8.0;net10.0` (generic math) + опционально `netstandard2.1` без generic math.

### 4.5. P/Invoke

- `[LibraryImport]` (source-generated) + `[SuppressGCTransition]` для коротких вызовов, `blittable`-сигнатуры (`ulong*`, `nint`).
- Порог «вызывать native или managed»: для 1–4 лимбов managed-код быстрее любого P/Invoke.
- Загрузка через стандартный поиск `runtimes/{rid}/native` (работает из NuGet без кода) + `NativeLibrary.SetDllImportResolver` для нестандартных случаев; при `DllNotFoundException` — тихий переход на managed fallback.

## 5. Ответы на идеи

**ARM64.** Нужен отдельный ассемблер: NASM умеет только x86. Варианты: GNU `as`/`clang` (Linux, macOS — синтаксис AArch64 один, отличия в директивах и префиксе `_` у символов на macOS) и `armasm64` (Windows on ARM) или `clang --target=aarch64-pc-windows-msvc` (тот же GNU-синтаксис — рекомендую, один исходник на три ОС). Ключевые инструкции: `mul`+`umulh` (128-битное произведение), `adds/adcs/sbcs` (цепочки переноса), `udiv` — **только 64/64**, деления 128/64 нет, поэтому `divrem_1` делается через предвычисленную обратную величину (Möller–Granlund), это даже быстрее `div` на x64. Регистры x19–x28 сохраняет вызываемая функция; на Apple `x18` трогать нельзя. Подробности — в [PLATFORMS.md](PLATFORMS.md).

**Умножение.** Сначала исправить базовый случай (A6): перейти от колонок к строкам (`mul_1` + `addmul_1`, без проверок диапазона во внутреннем цикле), на x64 с BMI2/ADX — `mulx` + две независимые цепочки `adcx`/`adox`. Затем Karatsuba (порог ~32–48 лимбов, подбирается бенчмарком), Toom-3 (~150–250 лимбов), отдельный `sqr` (возведение в квадрат примерно в 1,5 раза дешевле), затем NTT/FFT для миллионов бит. Подробности — в [ALGORITHMS.md](ALGORITHMS.md).

**Асинхронность / стримы / конвейер.** Честно: `async` для арифметики бесполезен — она упирается в CPU, а не в I/O, и `Task` здесь добавит только накладные расходы. Что реально полезно:
- **Параллелизм** (`Parallel.Invoke`) внутри Karatsuba/Toom/NTT для чисел от ~100 тыс. бит: три независимых подумножения на верхних уровнях рекурсии.
- **Потоковый ввод-вывод** — для огромных чисел, чтобы не держать строку целиком: `WriteTo(TextWriter/Stream/IBufferWriter<byte>)` и `Parse(ReadOnlySequence<byte>)`/`ParseAsync(Stream)`. Здесь `async` уместен, потому что это I/O.
- **Генерация цифр по мере вычисления** (spigot-алгоритмы, π/e до N знаков) — `IAsyncEnumerable<ReadOnlyMemory<byte>>` как надстройка, не в ядре.

**Вещественные числа.** Три разных типа, все поверх одного целого ядра:
- `BigDecimal` = `FullInteger` мантисса × 10^(−scale). Точные финансовые и инженерные расчёты, `+ − ×` точные, `÷` с заданной точностью и режимом округления.
- `BigFloat` = мантисса × 2^exp с фиксированной точностью в битах (как MPFR). Быстрее для научных расчётов; `sqrt`, `exp`, `ln`, π через Ньютона и AGM.
- `BigRational` = числитель/знаменатель с `gcd`-сокращением. Точная рациональная арифметика.

Порядок: `BigDecimal` (проще и востребованнее в .NET), потом `BigFloat`.
